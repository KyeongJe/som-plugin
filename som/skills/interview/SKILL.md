# interview — 시작 전에 모호도를 5% 아래로

## 무엇을 하는가

요청을 **구성 단위로 쪼개 확인**하고, 라운드마다 **가장 약한 지점에 질문 하나**를
던지고, 답변마다 **점수를 보여주고**, 모호도가 **5% 미만이 될 때까지 시작하지
않는다.**

```
Phase 0  문턱 고정 · 사용자에게 통보
Round 0  구성(토폴로지) 확인 — 이때는 점수를 매기지 않는다
Round 0.5  사용자가 이미 말한 것을 먼저 채점한다 (질문 0개)
Round 1..N  질문 1개 → 답변 → 채점 → 진행 표 → 다음 최약 지점
Phase 3  라운드 4/6/8 에서 반론 · 단순화 · 존재론 모드
Phase 4  스펙 결정화 → 승인 → conduct 로 인계
```

> 벤치마크: `oh-my-claudecode` 의 `deep-interview` 스킬. 차원·가중치·토폴로지
> 게이트·진행 표를 그대로 가져왔다. 다른 점 세 가지는 아래 **문턱** 절에 있다.

> **설정할 것이 없습니다.** 아래 명령의 `${CLAUDE_PLUGIN_ROOT}` 는 Claude Code 가
> 이 스킬을 읽어 들일 때 실제 경로로 바꿔서 넘겨줍니다 — 그대로 복사해 쓰면 됩니다.
>
> ```bash
> node "${CLAUDE_PLUGIN_ROOT}/bin/som.mjs" --help
> ```
>
> 이 파일을 저장소에서 **직접 열어** 읽는 경우에만 치환이 일어나지 않습니다.
> 그때는 `/som:doctor` 둘째 줄(`plugin  <경로>`)의 값으로 손수 바꾸세요.

## Phase 0 — 문턱 (차단 전제조건)

**어떤 안내·질문·채점보다 먼저** 문턱을 확정하고 첫 줄로 출력한다.

```bash
node "${CLAUDE_PLUGIN_ROOT}/bin/som.mjs" threshold
```

첫 줄은 **정확히** 이 형태다.

```
모호도 문턱: 5% (출처: 기본값)
```

문턱은 **상한이지 기본값이 아니다.** `som.interview.ambiguityThreshold` 로 더
조일 수는 있고 느슨하게 할 수는 없다. 설정이 5% 보다 크면 무시하고 그 사실을
출력한다. 벤치마크와 다른 세 가지:

| | 벤치마크 | som |
|---|---|---|
| 문턱 | 0.2, 자유 설정 | **0.05, 상한** |
| 라운드 상한 도달 | 현재 명확도로 **진행** | **시작 거부**, 스펙 미완성으로 남김 |
| 점수 계산 | 채점 프롬프트 안 | **코드** (`lib/domain/clarity.mjs`) |

세 번째가 중요하다. 5% 를 맞추라는 압박을 받는 채점자는 **모르는 것을 적어두고도
점수를 올린다.** 그래서 산식이 코드에 있고, 남은 항목(`gap`)이 비어 있지 않은
차원은 **0.89 로 제한**된다. 모른다고 쓰면서 명확하다고 할 수는 없다.

## 시작 안내

문턱 줄 다음에 이렇게 알린다.

> 시작 전에 몇 가지 여쭙겠습니다. 한 번에 하나씩, 답변마다 **모호도**를 숫자로
> 보여드립니다. **모호도가 5% 미만이 되면** 그때 작업을 시작합니다.
>
> **요청**: "{원문}"
> **유형**: {신규 | 기존 시스템 수정}
> **현재 모호도**: 100% (아직 아무것도 안 물어봤습니다)

**매 라운드마다 문턱을 다시 언급한다.** 사용자가 "왜 아직 시작 안 하지" 를
궁금해하는 상태로 두지 않는다.

## Phase 1 — 기록 만들기

문턱 줄과 안내를 낸 다음, **여기서 기록을 만든다.** 이 단계가 없으면 뒤의 모든
스니펫이 `<slug>` 을 못 찾아 `null` 에서 죽는다.

```bash
node "${CLAUDE_PLUGIN_ROOT}/bin/som.mjs" interview new "<사용자 원문>" --recipe <doc|prd|watch|analyze|build|data> [--brownfield]
# → slug 를 출력합니다. 이후 모든 명령에 그 값을 씁니다.
```

출력된 `slug` 를 이후 모든 호출에 쓴다. **`recipeId` 를 반드시 넣어라** — 레시피를
모르는 기록은 어떤 레시피도 승인하지 못하고, `clarityGate` 가 거부한다. 레시피마다
물어보는 것이 다르므로 이게 맞다.

`brownfield` 판정: 이 디렉토리에 이미 소스가 있고 사용자가 그것을 고치는 이야기를
하고 있으면 `brownfield`. 그러면 **기존 시스템 파악도** 차원(가중 0.15)이 추가된다.

## Round 0 — 구성 확인 (점수 없음)

Phase 1 초기화 후 **정확히 한 번**, 채점 전에 실행한다. 깊이 우선 질문이
가장 자세히 설명된 구성 하나에 과적합되는 것을 막는 게 목적이다.

1. 요청에서 **독립적으로 성공·실패할 수 있는** 최상위 구성을 뽑는다. 1~6개가
   적당하고, 넘으면 상위 수준으로 묶고 묶은 이유를 적는다. 구현 작업·필드·
   세부 기능은 사용자가 독립 결과물로 말한 게 아니면 최상위가 아니다
2. 확인 질문 하나를 던진다

```
Round 0 | 구성 확인 | 모호도: 아직 채점 안 함

이렇게 {N}개로 읽었습니다.
1. {이름}: {한 줄 설명}
2. ...

맞습니까? 추가 · 제거 · 병합 · 분리 · 보류할 것이 있나요?
```

선택지: **맞습니다** / **구성을 고치겠습니다** / **일부는 보류** / 자유 입력.

3. 답변을 받아 토폴로지를 잠근다

```bash
node "${CLAUDE_PLUGIN_ROOT}/bin/som.mjs" interview topology "<slug>" --components '[
  {"id":"ingest","name":"데이터 적재","description":"엑셀 읽기"},
  {"id":"report","name":"리포트","description":"HTML 출력"},
  {"id":"mail","name":"메일 발송","status":"deferred","reason":"이번 범위 아님"}
]' 
```

손으로 JSON 을 고치지 마라. `confirmTopology` 는 빈 목록·중복 id·전부 보류를
거부하고, 심어 넣은 `decided` 플래그를 벗겨낸다

**왜 이 게이트가 있는가.** "CSV 를 넣으면 정규화하고, 검토 UI 에서 인라인 댓글과
승인을 처리하고, 감사 가능한 리포트로 내보내는 파이프라인" 같은 요청에서 검토
UI 만 자세하다. 이 게이트가 없으면 검토 UI 는 완벽하게 명세되고 나머지 셋은
막연한 채로 모호도가 낮게 나온다. **전체 모호도는 가장 약한 구성의 값**이다 —
평균이 아니다.

## Round 0.5 — 이미 답한 것은 묻지 않는다

Round 0 직후, **첫 질문을 던지기 전에** 한다. 사용자가 처음 한 말에서 이미
확정된 차원을 먼저 채점한다.

"지난달 매출 리포트 만들어줘. 데이터는 이 엑셀에 있고, 주간 단위로, 영업팀
본다" 는 goal · constraints 를 이미 답한 것이다. 그걸 다시 묻는 것은 확인이
아니라 같은 말을 두 번 시키는 것이다. 그리고 사용자는 "아까 말했는데" 라고
생각하며 나머지 질문에도 성의를 잃는다.

```bash
node "${CLAUDE_PLUGIN_ROOT}/bin/som.mjs" interview round "<slug>" \
  --component "<구성 id>" --dimension goal \
  --question "(사용자가 먼저 말한 내용에서 채점)" \
  --answer "<사용자 원문에서 그대로 인용>" \
  --scores '{"goal":{"score":0.9,"justification":"원문: \"지난달 매출 리포트\" — 대상과 기간이 명시됨","gap":""},
             "constraints":{"score":0.8,"justification":"원문: \"이 엑셀\", \"주간 단위\" — 원천과 입도 확정","gap":"엑셀 경로 미확인"}}'
```

두 가지를 지킨다.

- **justification 에 사용자의 원문을 인용한다.** 인용할 문장이 없으면 그 차원은
  답한 것이 아니다. 점수를 주지 마라
- **`gap` 을 비우지 마라.** 원문이 암시만 한 부분은 gap 에 적는다. 그래야
  다음 질문이 그 자리로 간다

`asks` 슬롯도 마찬가지다. 인터뷰에서 이미 나온 답은 `asks` 에서 **다시 묻지
않고** 스펙에서 채운다 — `conduct asks --slots` 에 넣어 두면 남은 것만 나온다.

이걸 하면 완전히 명시된 요청은 **라운드 1회로 게이트가 열린다.** 실측: 네
슬롯이 다 채워진 R&R 요청은 Round 0 + Round 0.5 만으로 0%.

### 한 라운드에 차원 여러 개를 채점해도 되는가

**이미 답한 것을 기록할 때만 된다.** 위 예시처럼 한 번의 `--scores` 에 차원
두세 개가 들어가는 것은 질문 두 개가 아니라 **질문 0개**다 — 사용자는 이미
답했고 우리는 받아적는 중이다.

새로 물을 때는 여전히 하나씩이다. 아래 "절대 하지 않는 것" 의 이유가 그대로
적용된다: 답 하나가 점수 어느 쪽을 움직였는지 알 수 없으면 다음 질문을 어디로
보낼지도 알 수 없다.

## 라운드 — 질문 1개

### 질문 만들기

- **활성 구성 × 차원** 중 점수가 가장 낮은 쌍을 고른다
- 비슷하게 약한 구성이 여럿이면 **돌아가며** 묻는다. 방금 물어본 구성을 또
  묻지 않는다 (`lastTargetId`)
- 질문 앞에 **왜 지금 여기가 병목인지** 한 문장으로 밝힌다
- 기능 목록을 수집하지 말고 **전제를 드러내는** 질문을 한다
- 엔티티 이름이 계속 흔들리면 기능 질문을 멈추고 **"이게 근본적으로 무엇인가"**
  를 묻는다

| 차원 | 질문 방식 | 예 |
|---|---|---|
| 목표 | "정확히 무슨 일이 일어나나요?" | "'관리한다'고 하셨는데, 사용자가 처음 누르는 건 무엇인가요?" |
| 제약 | "경계가 어디인가요?" | "이건 사내망에서만 돌아도 되나요, 외부에서도 봐야 하나요?" |
| 완료 기준 | "무엇으로 됐다고 판단하나요?" | "다 만들어서 보여드리면, 무엇을 보고 '이거 맞다'고 하실까요?" |
| 기존 시스템 | "어디에 붙나요?" | "`app/sf_utils.py` 에 이미 접속 코드가 있습니다. 이걸 쓸까요, 일부러 따로 갈까요?" |
| 존재론 | "핵심이 무엇인가요?" | "거래선·매장·계정을 다 말씀하셨는데, 어느 쪽이 핵심이고 어느 쪽이 그것의 뷰인가요?" |

### 질문 형식

`AskUserQuestion` 을 쓴다. 머리줄에 항상 현재 상태를 붙인다.

```
Round {n} | 대상: {구성} | 차원: {차원} | 지금 여기인 이유: {한 문장} | 모호도: {n}% (문턱 5%)

{질문}
```

선택지는 맥락에 맞는 항목 + 자유 입력. **"모르겠다 / 미확정으로 두겠다" 를 항상
선택지에 넣는다** — 그게 정직한 답이고, 미확정으로 확정되면 그 항목의 모호도는
해소된 것으로 처리한다.

### 채점

답변을 받으면 차원별로 `score`(0.0~1.0) · `justification`(한 문장) ·
`gap`(아직 불명확한 것, 없으면 빈 문자열)을 낸다. 그리고 엔티티 목록도 낸다.

- **점수를 부풀리지 마라.** `gap` 을 적으면서 0.9 이상을 주면 코드가 0.89 로
  자른다. 자르면 진행 표에 그 사실이 그대로 찍힌다
- 이전 라운드 엔티티 이름을 **재사용**한다. 같은 개념에 새 이름을 붙이지 마라

가중치 (코드가 적용, 여기서 계산하지 않는다):

| | 목표 | 제약 | 완료 기준 | 기존 시스템 |
|---|---|---|---|---|
| 신규 | 0.40 | 0.30 | 0.30 | — |
| 기존 수정 | 0.35 | 0.25 | 0.25 | 0.15 |

기록과 계산은 엔진에 넘긴다. `<slug>` 는 Phase 1 이 출력한 값이고 `<구성 id>` 는
Round 0 에서 확정한 것이다. 둘 중 하나가 틀리면 명확한 한국어 오류가 난다 —
없는 구성이면 "구성 ... 이 없습니다", 없는 slug 면 `load()` 가 `null` 을 준다.

```bash
node "${CLAUDE_PLUGIN_ROOT}/bin/som.mjs" interview round "<slug>"   --component <구성 id> --dimension goal   --question "..." --answer "..."   --scores '{"goal":{"score":0.9,"justification":"...","gap":""},
             "constraints":{"score":0.6,"justification":"...","gap":"보존 기간 미정"},
             "criteria":{"score":0.5,"justification":"...","gap":"검증 방법 미정"}}'   --entities '[{"name":"거래선","type":"core domain","fields":["코드","명"]}]'
# 진행 표를 그대로 출력합니다. 문턱을 넘으면 exit 0, 아니면 exit 2.
```

### 진행 표 — 매 라운드 출력

`clarity.progressReport()` 가 렌더한다. 형태를 손으로 바꾸지 마라. 라운드마다
같은 모양이어야 **어느 질문이 숫자를 움직였는지** 사용자가 볼 수 있다.

```
라운드 3 완료 · 모호도 22% / 문턱 5%

| 차원 | 점수 | 가중 | 기여 | 남은 것 |
|---|---|---|---|---|
| 목표 명확도 | 0.95 | 0.40 | 0.380 | 없음 |
| 제약 · 경계 명확도 | 0.89 (보고 0.95) | 0.30 | 0.267 | 보존 기간 미정 |
| 완료 기준 명확도 | 0.45 | 0.30 | 0.135 | 검증 방법 미정 |
| **모호도** | | | **22%** | |

> 남은 것이 적혀 있는 차원은 0.89 로 제한했습니다. 모른다고 쓰면서 명확하다고
> 점수를 줄 수는 없습니다.

**구성**: 활성 2개 · 보류 1개 · 이번 라운드 대상 리포트
**엔티티**: 5개 · 안정 80% · 유지 3 · 개칭 1 · 신규 1 · 사라짐 0

**다음 질문**: 완료 기준 — 검증 방법이 없으면 다 됐는지 판단할 수 없습니다

모호도 22% · 문턱 5% — 17% 더 줄여야 합니다.
```

## Phase 3 — 반론 모드

같은 방향으로만 물으면 모호도가 낮아지면서도 계획이 나빠질 수 있다. 정해진
라운드에서 각도를 바꾼다.

| 라운드 | 모드 | 무엇을 하는가 |
|---|---|---|
| 4+ | 반론 | 지금까지의 전제 중 가장 위험한 것을 골라 반대로 가정하고 질문한다 |
| 6+ | 단순화 | "이 중 절반을 빼면 무엇이 남고, 그것으로 충분한가"를 묻는다 |
| 8+ | 존재론 | 모호도가 여전히 30% 이상이면 엔티티 정의로 돌아간다 |

## 소프트 · 하드 한계

- **라운드 3+** — 사용자가 "됐어, 시작해" 라고 하면 **모호도를 보여주고
  거부한다.** 대신 남은 항목을 '미확정'으로 확정하겠는지 묻는다. 미확정 확정은
  정당한 답이고, 그렇게 모호도가 내려가면 시작한다. **`gap` 텍스트에 "미확정"
  이라고 쓰는 것으로는 안 된다** — `acceptUnknown()` 을 호출해야 한다 (아래)
- **라운드 10** — "질문이 겉돌면 남은 항목을 미확정으로 확정하는 편이 낫습니다"
- **라운드 20** — **하드 캡. 시작하지 않는다.** 스펙을 `pending` 으로 쓰고
  무엇이 안 풀렸는지 적는다. 상한은 추측 허가가 아니라 **요청이 아직 이해되지
  않았다는 증거**다

이 마지막 항목이 벤치마크와 갈리는 지점이다. 거기서는 라운드 20에 "현재
명확도로 진행" 한다. 여기서는 안 한다.

## 정직한 출구 두 개 — 코드로 있는 것

`gap` 이 적힌 차원은 0.89 로 잘리고, 그건 **가중치 × 0.11 만큼 모호도를 남긴다.**
신규 작업에서 두 차원에 `gap` 이 있으면 하한이 6.6% 라서 **라운드를 몇 번 돌려도
5% 아래로 안 내려간다.** 정직하게 "모른다" 고 적은 사용자가 영구히 갇히는 것이다.

그래서 출구가 둘 있고, **둘 다 API 다.** 산문 안내가 아니다.

```bash
# 1. 이 항목은 모르는 채로 진행하기로 확정한다 — <slug> 는 Phase 1 의 출력값
node "${CLAUDE_PLUGIN_ROOT}/bin/som.mjs" interview accept "<slug>" \
  --component "<구성 id>" --dimension constraints \
  --note "정책 확정 후 별도로 정하기로"

# 2. 이 구성 자체를 이번 범위에서 뺀다
#    iv.deferComponent(rec, "<구성 id>", "이번 범위 아님")
```

**`gap` 텍스트는 지우지 않는다.** 기록에 남고 스펙의 `미확정` 절에 들어간다 —
여전히 모르는 것이고, 다만 더 이상 **결정되지 않은** 것이 아니다.

"아직 못 알아냈다" 와 "모르는 채로 가기로 했다" 는 다른 상태이고, 두 번째만
게이트를 연다. 그래서 채점자가 문구로 흘러들 수 없게 **사람이 세우는 플래그**다.

**채점 결과에 `decided` 를 직접 넣어도 무시된다.** `addRound()` 가 벗겨낸다 —
채점자가 자기 gap 을 스스로 확정할 수 있으면 0.89 컷이 자발적 규칙이 되고, 그건
컷이 있는 이유 자체를 없앤다. 실측으로 확인한 우회로다. 반대로 사람이 한 번
확정한 것은 이후 라운드의 재채점으로 되돌아가지 않는다.

## Phase 5 — conduct 로 인계

스펙을 보여주고 **명시적 승인**을 받는다. 승인 없이 실행으로 넘어가지 않는다.

승인 후 `conduct` 스킬을 호출한다. 스펙의 답변이 레시피의 `asks` 슬롯을 채우므로
**같은 질문을 두 번 하지 않는다.** conduct 의 `plan()` 이 인터뷰 기록을 다시 읽어
문턱을 확인하므로, 승인만으로 게이트가 열리는 것은 아니다 — 숫자가 열어야 한다.

## 절대 하지 않는 것

- **한 라운드에 질문 두 개를 묻지 않는다.** 점수를 어느 답이 움직였는지 알 수
  없게 된다. (예외는 Round 0.5 뿐이다 — 거기서는 묻는 게 아니라 사용자가
  이미 한 말을 받아적는 것이라 질문이 0개다)
- **모호도를 숨기지 않는다.** 매 라운드 숫자와 문턱을 같이 보여준다
- **문턱을 느슨하게 하지 않는다.** 설정으로도, 사용자 요청으로도 5% 위로는 안
  간다. 대신 미확정 확정이라는 정당한 출구를 제시한다
- **모르는 것을 채워 넣지 않는다.** 답이 없으면 '미확정' 으로 기록한다
- **`gap` 을 적으면서 높은 점수를 주지 않는다.** 코드가 자르고, 표에 찍힌다
- **하드 캡에서 진행하지 않는다.** 미완성 스펙을 남기고 멈춘다

## 상태

`.som/interview/{slug}.json` 에 라운드별 질문·답변·점수가 전부 남는다. 인터뷰는
자기가 승인한 런보다 오래 산다 — 세션이 죽거나 압축돼도 같은 답변이 게이트를
그대로 연다. 이미 답한 질문을 다시 묻는 것이 사람을 가장 빨리 떠나게 한다.

`--resume <slug>` 로 이어간다.
