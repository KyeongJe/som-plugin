이 문서 자체가 검증이다
이 페이지는 som 의 문서 엔진이 렌더했다. 위 숫자는 저장소에서 빌드 시점에 측정한 값이며, 손으로 적은 값이 아니다. 엔진이 자기 설명서를 못 만들면 준비된 게 아니다.

2무엇을 해결하나

지금의 문제

  • 반복 업무 세 종류가 매번 손으로, 매번 다른 형태로 나온다
  • 데이터 분석 — Snowflake 파이프라인을 프로젝트마다 재구현
  • 내부 도구 개발 — 기획·구현·검증 순서가 매번 다름
  • 팀 운영 문서 — R&R·KPI·팀 정의에 공통 포맷이 없어 일회성 산출물
  • 결과: 팀원이 같은 품질로 재생산할 수 없다

som 의 대응

  • 세 업무를 같은 5-stage 게이트 골격 위에 올린다
  • 게이트 통과 조건을 산문이 아니라 코드로 판정한다
  • 산출물은 검증된 공통 포맷 하나에서 파생된다
  • Orca 가 없는 팀원도 같은 바이트를 재현할 수 있다

35-stage 게이트

게이트는 통과 조건을 만족해야 다음 스테이지가 열리는 구조적 검사다. 판정은 코드가 한다.

게이트스테이지 전이통과 조건 (코드가 확인)해제

동시성은 이 플러그인이 정한다

  • Orca 는 스케줄링·동시성·충돌 판단을 하지 않는다 — 루프를 직접 쓴다
  • writes 글롭이 교차하는 두 태스크는 다음 wave 로 미룬다 (워크트리 격리 아님)
  • 동시 워커 기본 3, current 체크아웃에서 하드 캡 4
  • 중첩 깊이 1 — 코디네이터 1 + 워커 N 평면 구조

느린 것과 실패한 것은 다르다

  • check --wait 타임아웃 · count:0 은 체크포인트다 — 실패가 아니다
  • 코딩 태스크 15~60분은 정상. heartbeat 는 살아있다는 뜻이고 끝났다는 뜻이 아니다
  • 태스크 3회 연속 실패 → Orca circuit-break. 동일 설정 재시도 금지
  • G2 불일치 → 재개 최대 2회, 그 뒤 사람에게 에스컬레이션

4코디네이터 루프 — 두 프로세스, 하나의 소비자

check 는 FIFO delivery 상태를 변경하므로 정확히 한 프로세스만 호출해야 한다. 그래서 소비자(watcher)와 결정자(router)를 분리했다.

이 구조에서 공짜로 얻는 것

  • watcher 는 호스트 관리 Monitor 프로세스라 컨텍스트 압축에 면역이다
  • router 가 배치 처리 중 죽으면 ack 가 안 되므로, 다음 세션의 watcher 가 같은 배치를 그대로 재발행한다 — 인바운드 durability 가 별도로 필요 없다
  • 락 없음. 파일당 단일 작성자. 모든 쓰기는 tmp → fsync → rename
  • Orca 가 아는 것은 전부 Orca 에서 재도출한다. 디스크를 신뢰하지 않는다

6Snowflake 안전 — 읽기 자동, 쓰기는 승인

쓰기에서 경보가 올라가는 네 가지

  • UPDATE · DELETE 에 WHERE 가 없다 — 대상 테이블의 모든 행
  • OR REPLACE — 같은 이름이 이미 있으면 그 내용이 사라진다
  • CALL — 프로시저 내부는 이 도구가 볼 수 없고, 볼 수 없다고 말한다
  • 대상 객체명을 읽어내지 못했다 — 추측을 출력하는 대신 그렇다고 말하고 심각도를 올린다. 틀린 대상 줄은 없는 대상 줄보다 나쁘다

읽기는 막지 않는다 — 알려줄 뿐이다

  • 상한이 없다. byte · 행 · statement timeout 제한을 전부 없앴고, LIMIT 을 몰래 끼워 넣지 않는다
  • 그 LIMIT 주입이 가장 나빴다 — 41만 행 추출에 1,000행을 돌려주면 잘린 결과가 완전한 결과와 똑같이 생긴다
  • ON/USING 없는 join(cartesian) 은 실행 전에 알려준다
  • EXPLAIN USING JSON 으로 사전 스캔 견적 — 크레딧 0
  • 동일 stmt hash 24시간 캐시 — 같은 질문을 두 번 돌리지 않는다
  • 매 실행 ledger 기록 → DELIVER 부록에 산출물당 비용 표로 노출. 비용 가시화와 비용 통제는 다른 일이고, 원치 않은 쪽은 통제였다
기존 스크립트는 막지 않는다
PreToolUse 훅은 이 플러그인 밖에서 Snowflake 에 닿는 명령과 파일을 거부하지 않고 경고한다. 팀에는 이 플러그인이 생기기 전부터 쓰던 스크립트가 있고, 그것을 막는 것은 som 과 무관한 업무를 세우는 일이었다. 경고가 알려주는 것은 그 실행이 원장 밖이라는 사실이다 — 나중에 '언제 무엇을 했나' 를 되짚을 때 그 줄만 비어 있다.
권한은 여전히 role 이 정한다
래퍼는 defense-in-depth 다. 무엇을 쓸 수 있는지의 근본은 Snowflake role 의 grant 이고, 사람마다 필요한 만큼만 주도록 DCOE 에 요청하는 것이 이 설계 전체에서 가장 가치 높은 조치다.

비대칭이 의도적이다
게이트는 엔진이 물어볼 수 있는 예/아니오다. 하드 플로어는 사람이 자기 턴에 직접 요구를 타이핑해야 하는 것이다. Snowflake 쓰기는 플로어에서 게이트로 내려왔다 — 근거였던 '사람의 예를 쓰기로 바꾸는 코드 경로가 없다' 가 테이블을 만들어야 하는 날 깨졌기 때문이다. 어느 레벨에서도 자동이 되지 않는다는 점은 그대로다.

Orca 가 없는 팀원의 재현 경로

  • 5 stage 를 한 세션에서 순차 수행. 게이트는 stop-and-ask 로 격하
  • 에이전트 저작물은 IR JSON 하나. 렌더는 python -m somdoc build
  • skeleton · theme · emitter 가 전부 플러그인 파일이라 산출물이 바이트 비교 가능
  • 가장 강한 degradation: 에이전트를 건너뛰고 IR + 명령 한 줄만 넘겨도 동일 산출물

경계 — 무엇을 쓰지 않는가

  • 다른 플러그인을 호출하지 않고 그 상태 폴더를 읽지도 쓰지도 않는다
  • Orca 의 orchestration 스킬이 CLI 문법의 권위다 — 여기 요약하지 않는다
  • Artifact 발행 경로가 없다. 산출물은 로컬 파일뿐
  • 다른 플러그인이 트리거로 쓰는 문구를 피한다 — 가로채면 도구가 아니라 방해가 된다
